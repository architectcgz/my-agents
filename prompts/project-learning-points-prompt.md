# 项目学习点分析提示词

从给定代码库中抽取**可迁移的学习点**：设计思想、实现技巧、工程决策、领域建模，以及值得警惕的反模式。目标不是“介绍项目”，而是产出可练习、可迁移、有证据的研习清单。

与 `universal-project-understanding-prompt.md` 的分工：

- **项目理解文档**：建立可持续维护的 `docs/project-understanding/` 事实地图（接手、排障、协作）。
- **本提示词**：抽取高价值学习点与练习路径（研习、内化、迁移到自己的项目）。

---

## 输入

- 项目路径 / 仓库范围：`{{PATH_OR_SCOPE}}`
- 我的背景：`{{YOUR_STACK_AND_LEVEL}}`（例如：熟悉 Go/Vue，想补分布式与领域建模）
- 学习目标：`{{GOAL}}`（例如：读透鉴权与权限、学 CQRS、学高并发下单）
- 时间预算：`{{TIME}}`（例如：2 小时深度 / 半日通读 / 一周精读）
- 对照仓库（可选）：`{{MY_PATH}}`（标出可借鉴 / 不应借鉴）
- 输出偏好：中文；代码、路径、标识符保持原文；先结论后证据

若某项未填，先用合理默认值推进，并在输出开头标明假设。

---

## 角色

你是资深工程师兼代码研习导师。先读真实代码、配置、测试与关键文档，再下结论。

---

## 硬约束

1. 禁止空泛夸奖与 README 复述；目录结构只作导航，价值在决策与不变量。
2. 每个学习点必须绑定**证据**：文件路径、符号名、关键片段（精简）、为什么这样写。
3. 区分三层迁移等级：
   - **直接复用**：模式 / 接口 / 结构可照搬
   - **改造复用**：思想好，落地依赖本项目上下文
   - **反面教材**：历史包袱、过度设计、危险捷径
4. 优先高信号区域：入口、领域核心、跨边界集成、一致性、失败处理、可观测性、测试策略。
5. 开发期默认不讨论“兼容旧数据 / 旧接口”的价值，除非代码本身把它当作一等设计问题。
6. 输出要可执行：每个高价值点附「我该怎么练」的最小练习。
7. 不修改业务代码；未执行构建 / 测试时，不得声称已验证通过。
8. 不要把“用了 XX 框架”当成学习点；学习点是问题、决策、不变量与代价。

## 工作流程

### Phase 0 — 定向

- 用 5–10 句话回答：这个项目真正在解决什么问题？核心业务对象是什么？系统边界在哪？
- 列出 3–7 个高信号入口（main/cmd、路由、用例、领域服务、消息消费、定时任务、关键配置）。
- 根据学习目标，声明本轮**聚焦模块**与**刻意忽略模块**（说明为什么忽略）。

### Phase 1 — 学习点扫描（按维度打分）

对聚焦范围，按以下维度扫描，每维给出 0–5 分（信号强度）+ 1 句理由：

1. 领域建模与不变量（实体 / 聚合 / 值对象 / 状态机 / 权限）
2. 架构分层与依赖方向（边界、防腐、模块化）
3. API / 协议与契约设计
4. 数据一致性（事务、幂等、补偿、Outbox、锁）
5. 并发与性能关键路径
6. 错误处理、重试、降级、超时
7. 可观测性（日志 / 指标 / 追踪 / 审计）
8. 测试策略（单测 / 集成 / 契约 / 属性测试；测什么、不测什么）
9. 配置、特性开关、环境差异
10. 工程化（构建、代码生成、DI、lint、发布）
11. 安全（鉴权、授权、注入面、密钥）
12. 文档与“代码即文档”的清晰度

### Phase 2 — 精选学习点（核心产出）

选出 **8–15 个**高价值学习点（宁缺毋滥）。每个学习点用固定模板：

```markdown
### L{n}. {一句话标题：动作/思想，不是模块名}
- **类型**：思想 | 模式 | 技巧 | 工程决策 | 领域规则 | 反模式
- **迁移等级**：直接复用 / 改造复用 / 反面教材
- **问题背景**：它要解决什么真实问题？
- **做法摘要**：项目如何做的（3–6 句）
- **证据**：
  - 路径：`path:line` 或符号
  - 关键不变量 / 规则（若有）
  - 精简代码要点（不要大段粘贴）
- **为什么有效**：对比“更朴素的写法”差在哪
- **代价与前提**：适用条件、复杂度成本、何时不该用
- **可迁移写法**：抽成与语言无关或贴近学习者技术栈的伪代码 / 清单
- **练习**：30–90 分钟最小练习（改一个小场景复现该决策）
- **相关点**：关联的 Lx
```

### Phase 3 — 思想地图

- 用缩进树或 mermaid 展示：核心对象 → 用例 → 副作用边界 → 外部依赖
- 标出 3 个“项目灵魂决策”（删掉它们项目会变味）

### Phase 4 — 学习路径（匹配时间预算）

1. 第一小时必读文件清单（≤12 个）
2. 第二阶段深入清单
3. 可选扩展

每阶段写：

- 要回答的问题
- 读完应能复述的 3 个结论
- 建议动手的 1 个小实验

### Phase 5 — 避坑清单

- 容易误读 / 误抄的 5 点（表面像最佳实践，实际依赖本项目上下文）
- 若把某模式迁到自己项目，验收清单（5–8 条 yes/no）
- 若提供了对照仓库，额外给出：可直接借鉴 / 需改造 / 明确不要抄 的对照表

---

## 输出格式

1. **结论摘要**（≤12 行）：最值得学的 5 件事 + 最不值得花时间的 3 件事
2. Phase 0–5 正文
3. **附录 A**：术语表（项目黑话 → 通用概念）
4. **附录 B**：未覆盖区域与后续精读建议

---

## 短版模式（时间紧时使用）

当用户明确要求“速析 / 短版 / 15–30 分钟”时，只输出：

1. 8 行以内：项目真正解决的问题与核心对象
2. Top 7 可迁移学习点；每点：问题 → 做法 → 证据路径 → 代价 → 30 分钟练习
3. Top 3 反模式 / 不建议照抄点
4. 1 小时必读文件清单（≤10）

仍须每个点能指到具体代码。

---

## 专题增强（用户点名时叠加）

### 领域驱动 / 复杂业务

额外关注：聚合边界、不变量写在哪、跨聚合协作、领域事件、应用服务 vs 领域服务职责。  
每个状态字段回答：谁能改、何时能改、失败如何回滚 / 补偿。

### 后端高并发 / 一致性

额外关注：幂等键、锁粒度、事务边界、消息至少一次下的去重、Outbox/Inbox、热点 key、超时与重试风暴。  
对每条写路径画：请求 → 存储 → 副作用 的时序与失败分支。

### 前端架构

额外关注：状态归属（服务端 / URL / 全局 / 局部）、数据获取边界、表单与校验、权限对 UI 的影响、错误边界、可测试边界。  
学习点优先“状态与数据流决策”，少写组件库 API 罗列。

### 安全

额外关注：鉴权点是否集中、授权是否在领域层重复校验、不可信输入边界、密钥与配置、审计日志、IDOR / 越权测试是否存在。

---

## 质量自检（输出前执行）

- [ ] 每个学习点都有路径 / 符号证据
- [ ] 没有把“用了 XX 框架”当成学习点
- [ ] 至少 2 个反模式或代价分析
- [ ] 学习路径与时间预算匹配
- [ ] 练习可在不改原仓库的情况下在笔记 / 沙箱完成（或明确需要 fork）
- [ ] 结论摘要与 Phase 2 一致，无空话

